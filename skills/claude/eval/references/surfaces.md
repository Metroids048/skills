# 按被测物形态选打法

评测本身是一样的：一支人群带着自己的目的真用一次，我们从他们的行为里读出还想不想接着用。换成不同形态的被测物，只有三处会变 —— **从哪条真实入口进、过程留什么证据、这个人的差异应该体现在哪**。

**默认以本页为准**：eval 默认不碰 mirofish CLI，所以下面几族的打法、证据要求和"最容易怎么坏"就是全部依据；要量化时按该族的维度自己写 judge 指标与判分 rubric（eval 默认语义化反馈，`measure` 允许为空）。

只有用户明确要求接平台时，才现取机器可读的那份预设（别抄进脑子里）：

```bash
mirofish surfaces                 # 全部被测面 + 分族
mirofish surfaces image --json    # 某面的完整预设(真实入口/证据清单/case 输入清单/指标含 rubric/常见走偏)
mirofish new methodology --surface image -o mth.json   # 已按该面预填指标与 rubric 的骨架
```

预设是起点不是配额。窄问题砍到一个指标也对；这个面上有更要紧的维度就自己加 judge 指标，把 rubric 写清。但取了预设就**别绕开它另造一套同义指标** —— 同类评测之间要能比，换个 key 名就断了比较。

下面提到「留截图」时，机制都是同一套（细节见 [protocol.md](protocol.md) §8）：截图存进 session 的 `evidence/` 下，**相对 `evidence/` 根**的路径写进该步 `shots`（步末看到的画面）或 `operates[].shot`（某一次具体操作之后的画面）。本地 `mirasim eval` 页面据此逐步渲染；接了平台时上送姿势见 [cli.md](cli.md)。

下面写预设里放不下的东西：这一族的人该怎么写、派发时该给什么、证据怎么真拿到、以及**这一族的评测自己最容易怎么坏**。

「人的差异放在哪」说的是**这一族该往 `memory.episodes` 里写哪几类经历**——差异不是靠 profile 里换个形容词做出来的，是靠他各自想起了不同的事。三层怎么写、密度多少、经历怎么写才会被想起，见 [cast.md](cast.md)。

## 界面类 —— 网页 `web` / 移动应用 `app`

**人怎么碰到它**：在界面里点。

**人的差异放在哪**：不是职业名，是「他过去用过什么同类东西」（决定他会去哪里找功能）和「他手上有多急」（决定他愿意试几次就走）。两个都写厚，行为立刻分叉。

落成经历：他上次在哪个具名产品里找同一个功能、找到没有（决定他这次先点哪里）；他被哪个界面骗过一次（决定他信不信页面上的话）；他上次赶时间时怎么放弃的（决定他这次第几次失败就走）。

**派发要给的**：起始 URL 或包名、账号初态（全新访客／已登录测试账号／有历史数据）、窗口尺寸或设备、以及一句硬约束 —— **他只能看到这个界面，不能读源码、不能看仓库**。

**真浏览器 / 真设备从哪来**：web（网页）case 走 **agent-browser** —— 每 case 一个 `--session` 隔离的浏览器上下文，子代理自己按可见文字挑 ref 真点真输，每次操作后截图落进 evidence。隔离资源怎么造、预热为什么必须主代理做、并行有哪几个静默失效的坑，**派发前必读** [browser.md](browser.md)。**app 端（Android / iOS / mac 应用）的驱动已退役，app 类 case 目前一律不派** —— 缘由与不许怎么兜底见 [app-cases.md](app-cases.md)。两页共守同一条红线：**绝不驱动用户自己的浏览器与应用**。

**证据怎么真拿到**：每一步页面变化后截一张图 —— 步末画面进 `shots`，中间每次点击/输入之后的画面进对应 `operates[].shot`。关键文案原样摘进 `observation`，别转述。填了什么、点了哪个东西按**用户能看见的字**写，不写选择器 —— 写选择器就说明这是自动化脚本在跑，不是人在用（agent-browser 的 `snapshot -i` 返回的 ref 本身带可见文本，按文本挑 ref 即满足这条）。

**步数预算**：8–15 步。真人不会在一个页面上试二十次。

**这一族的评测最容易怎么坏**
- 只读 HTML 或只读源码就下「交互没问题」的结论。做不到真点就把结论边界改写成内容检查，别冒充。
- 执行层按序号乱点（「点了第 3 个按钮」），判决被污染成产品的问题。按可见文字定位。
- 复用了上一个 case 的登录态或浏览器 profile，把「已经熟了」当成「第一次就会」。
- 把「页面上写了」当成「用户看懂了」。只认他自己说出来的理解。

## 对话类 —— Agent `agent` / 模型 `model`

**人怎么碰到它**：跟它说话。

**人的差异放在哪**：他对这类东西的**预期**（以为它能一句话办完，还是准备好要来回带它），以及他**愿意交出多少上下文**（有人只给一句，有人贴一整篇）。预期差是这一族流失的主要来源，差异必须落在这里。

落成经历：他具体用过哪些同类的（具名 + 哪一年 + 在上面干成/没干成什么），哪一次它自信地给了个错答案而他没当场发现（决定他这次会不会验），他自己写过/维护过什么（决定他能看懂多深），以及他对某个同类工具的既有判断和这判断是怎么来的——写他对**别的** agent 的看法，不写他对被测物的看法。

**派发要给的**：接入方式（命令／端点／网页入口）、**会话必须全新无历史**这条硬约束、他自己那件真事（带他真实的材料，不是「帮我写个测试」这种空任务）、以及往返预算。

**证据怎么真拿到**：每一轮他说了什么（`say`）、它回了什么（`observation`）都留，别只留最后结论 —— 期望差就藏在中间那几轮。它中途做了什么可见动作（调了工具、改了文件）如实记进 `observation`。它有界面就顺手留截图。

**步数预算**：4–10 轮。追问超过这个数，真人早走了。

**这一族的评测最容易怎么坏**
- 主代理替被测 agent 把答案补上了。它答不出来就是答不出来，这正是要观察的。
- 用了带历史的会话，把上文当成它的能力。
- 把 rubric 塞进 packet，用户于是照着 rubric 提问 —— 自证预言，整轮作废。
- 只统计对错。真正要看的是**用户能不能察觉它错了** —— 能被察觉的错和不能被察觉的错，代价差一个量级。

## 工具类 —— Skill `skill` / 命令行 `cli`

**人怎么碰到它**：装进自己的活里。

**人的差异放在哪**：技术水平（第一次碰这类工具，还是熟手来评估要不要换掉现有的），以及**他现在的工作流里已经有什么**（已有替代品的人和白手起家的人，判断标准完全不同）。

落成经历：他现在的工作流具体由什么组成（具名工具 + 版本 + 哪年开始用），上次迁移是从什么换到什么、为什么换、迁移里最疼的是哪一步，他被哪个 quickstart 骗过（决定他会不会照文档走），以及他机器上已经有什么（决定他会不会踩依赖坑）。

**派发要给的**：隔离的 cwd（`mktemp -d`）、不继承你本机配置与已装依赖的干净环境、安装命令、**他只能看公开说明**这条约束、一件他手上的真任务。不是「试试这个工具」—— 那不是任务。

**证据怎么真拿到**：真实命令 + stdout/stderr + 退出码，一步一条原样留。安装到第一次跑通之间的**每一次失败都要留** —— 上手摩擦全在这一段，跳过它等于把最贵的信号丢了。需要整段回放就开 `runtime.record`（asciicast）。

**步数预算**：10–20 步。摸索是这一族的正常行为。

**这一族的评测最容易怎么坏**
- 读源码代替真跑。用户不读你的源码。
- 给了一个直接返回结果的 Local Use，绕过正在验证的入口 —— 后门。判「新用户能不能跑通 CLI」时不能给一个替他跑 CLI 的能力。
- 继承了你本机已装好的依赖，把「我这儿能跑」当成「谁都能跑」。
- 把 shell 执行写成「点击了界面」。记录必须与实际入口一致。

## 成品类 —— 文档 `document` / 图片 `image`

**人怎么碰到它**：读它、看它。没有交互，只有理解。

**人的差异放在哪**：**背景知识水平**（术语门槛对不同读者是完全不同的东西，这是这一族最强的分叉变量）、他要据此做的那个决定、他会花多久看（三十秒扫一眼和坐下来读十分钟看到的是两份东西），以及**他拿到之后要把它用到哪去**——自己看懂就完了，还是要转手带到别人面前（投屏、发给客户、放进自己的材料）。差异写不厚，几位读者会塌成同一个「认真的平均人」，这一族的评测就白跑了。

**几位读者全是「只为读懂而来的人」，是这一族最贵的塌陷。** 读懂了就走的人，没有理由关心这份东西够不够格拿出去、看着专不专业、敢不敢署自己的名。于是呈现质量永远不进证据链：读懂、可信、够不够做决定这几维可以全是高分，而它到底能不能被原样拿出去用，从来没有人问过。所以至少要有一个人的真实用途是**转手用**——他必须把它带到别人面前，「能不能原样用」对他就是当场要做的判断。注意这是给他一个真实用途，**不是**让他留意排版，后者才是把评测口径塞进轨迹。

落成经历：他做过/看过哪些同类的东西（决定他拿什么当参照系——见过一百张架构图的人和第一次见的人视线完全不同）、他上次因为看错一张图做了什么决定、他自己讲过/画过什么（决定他会不会替作者补全意图）、哪个术语他其实一直没搞懂但不好意思问（这一条最出信号），以及**他上次把别人做的材料拿去自己场合用时发生了什么**（原样用了／自己重做了一版／当场被人问住）——返工过的人这次会当场判断值不值得再返工一次，而这个判断正是呈现质量唯一的行为证据。

**派发要给的**：最终形态的文件或渲染后的地址、他实际会在多大尺寸下看它、看它的场合（投屏演示／手机上刷到／文档里配图）、**他只有这份东西、没有讲解人**这条硬约束、他要做的判断。

**证据怎么真拿到 —— 这一族的关键**：

必须先渲染成成品，再让子代理**用视觉能力看真实像素**。

```bash
# HTML / SVG 成品:按真实观看尺寸截图
npx playwright screenshot --viewport-size=1440,900 file:///abs/path/diagram.html shot.png
# PDF:逐页转图再看
# Markdown:版式重要时先渲染,不重要时才可直接读源文本(并在结论里说明这是内容检查)
```

那张图本身写进 `shots`。**这一族没有画面证据等于没有证据。** 文件名、alt 文本、生成它的代码，都不能代替看图。他先看到什么、视线往哪走、哪里看不清，如实记录；他对内容的**复述原话**留下 —— 复述错了就是这份东西没说清，这比任何评分都直接。

**步数预算**：3–6 步。看东西不需要很多步，需要的是看得真。

**这一族的评测最容易怎么坏**
- 只读 markdown 源码或只看生成代码，就说看过了。
- 只在大屏原尺寸下看，漏掉真实观看尺寸下的可读性问题。
- 把「元素都画上了」当成「看懂了」。
- 在 scenario 里写「留意排版好不好」—— 把评测问题塞进了轨迹，读者于是变成审稿人。
- 一支读者里没有一个人要转手把它拿出去用 —— 呈现质量没有承接它的行为，越跑越只剩细枝末节。
- 读者自己动手返工了（裁剪、重排、另画一版），却因为「他最后还是办成了事」判成高分 —— 返工成本必须落在 `usable_as_is` 上，不然这个信号每轮都出现、每轮都被记成他的个人习惯。

## 判错族的代价

族判错了，整轮证据不成立，而且**看起来像成立的**，所以特别贵：

- 拿源码读一遍当成用过网页 → 得到的是内容意见，不是使用体验。
- 拿 markdown 源文件当成看过成品文档 → 版式、层级、视线全部没被验证。
- 给 agent 一个带上文的会话 → 验的是「熟练用户第二次用」，不是第一次用。
- 在你自己配好的环境里跑工具 → 上手成本被抹掉了，而上手成本往往就是它没人用的原因。

拿不到真实入口不是失败，**冒充拿到了才是**。降级去做更窄的验证可以，但必须同时改写结论边界：说清这轮验了什么、没验什么。
