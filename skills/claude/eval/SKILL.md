# eval

## 你的价值

给当前工作接入它本来缺少的外部用户视角。让相关的人在自己的情境里真实行动，观察他们理解了什么、选择了什么、在哪里受阻，再把这些证据交还给主代理，帮助它作出更好的下一步判断。

这不是替用户打分，也不是让子代理写评审意见。仿真用户只负责办自己的事；主代理负责理解反馈、处理取舍，并在获得授权时修改目标。

仿真与分析始终在本地完成，**默认全程不碰 mirofish CLI**——不探测、不安装、不登录、不检索、不回写。它只是一条可选通道，负责复用和沉淀 persona、scenario、methodology、trace、feedback 与迭代谱系，从不参与仿真或判断；**只有用户在本次对话里明确要求**（"接平台 / 传到 mirofish / 留档到平台 / 复用平台资产"）才启用，姿势见 [references/cli.md](references/cli.md)。用户没提就当它不存在：CLI 没装是常态而非缺陷，别去装、别提示用户去装、也别写进反馈。

## 先确定这次要走多深

从用户原话判断授权，不要擅自升级任务：

- 用户只想看看、验证或了解反应：运行一轮，交付反馈，不改目标。
- 用户明确授权优化或修复：先取得外部使用证据，再修改并用新上下文复验受影响的路径。
- 用户要求持续改进、充分验证或达到某个结果：自主循环，直到结果获得相称证据、继续仿真不再增加决策信息，或剩下必须由用户决定的取舍。

只有缺失信息会改变目标、授权范围或结果解释时才追问；信息足够就直接推进。

## 先看被测物是哪一类

这一条决定后面全部：什么才算真用过它、每步该留什么证据、默认量哪几维。四个族按人怎么碰到它分：

| 族 | 被测物 | 人怎么碰到它 | 真实入口 |
| --- | --- | --- | --- |
| 界面类 | 网页、移动应用 | 在界面里点 | 真浏览器 / 真设备，**每步留截图** |
| 对话类 | Agent、模型 | 跟它说话 | 无历史新会话，留完整往返 |
| 工具类 | Skill、命令行 | 装进自己的活里 | 隔离目录真装真跑，留命令与退出码 |
| 成品类 | 文档、图片 | 读它、看它 | 按最终形态渲染后再读 / 看真实像素，**留所看画面** |

每族的人该怎么写、派发要给什么、证据怎么真拿到，见 [references/surfaces.md](references/surfaces.md)——**默认就以这页为准**。要量化时按该族的维度自己写 judge 指标与判分 rubric（eval 默认语义化反馈，`measure` 允许为空）。只有用户要求接平台时才现取该面预设：`mirofish surfaces` 列全部被测面，`mirofish surfaces <面>` 给该面的完整打法（真实入口、证据清单、case 输入清单、默认指标含 rubric、这个面上最常走偏的地方），`mirofish new methodology --surface <面>` 直接产出已预填这些的骨架 —— 那时优先沿用预设的 key，**别另造一套同义指标**，同类评测之间要能比。

**别把一类当另一类**：拿源码读一遍不叫用过网页；拿 markdown 源文件读一遍不叫看过成品文档；给 agent 一个带上文的会话不叫第一次用；在你自己配好的环境里跑工具，上手成本就被抹掉了。判错了族，整轮证据都不成立，而且看起来像成立的。拿不到真实入口不是失败，冒充拿到了才是 —— 降级做更窄的验证可以，但必须同时改写结论边界。

## 把请求变成一次外部使用

先写下一句真正要回答的问题。它应指向用户接下来要作出的决定，而不是宽泛的“好不好”。同时固定被验证版本、真实入口、可见环境和完成证据。

然后组织 cases：

1. 找出哪些差异会改变理解、路径、约束或最终选择；每个差异形成一个 persona 假设。
2. 给每个 persona 一件自然发生的事。Scenario 写目的、处境与可观察的收束，不写操作步骤、疑似缺陷或正确答案。
3. 需要多少视角由仍待回答的不确定性决定。一个窄问题可以只有一个 case；复杂问题可以有更多。不要凑人数、正反例或固定角色。本地形态适合个位数到十几个 case——每个 case 都是子代理真实操作，算力和时间都是真花的；更大规模的批量评测超出本技能定位，如实告知而不是硬跑。
4. 默认直接在本地生成完整定义，不去检索平台库存。只有用户要求接平台时才先检索已有资产，且只有行为逻辑和当前情境真正贴合才复用，否则照样新造。按 cast.md 的密度新造一个人不便宜——接了平台且库存真贴合时，复用是最大的单项节省。

**要 Loop 时，广度花在第一轮。** 首轮把问题面一次铺开——不同用途的人都放进来，不只是不同背景的人；后面几轮才收窄成复验。反过来做（用一小撮人跑基线，往后每轮又都是同一批），分数会一轮轮往上走、改动会一轮轮变细，而这批人没碰到的那一面，直到收口都没人看过。

**被测物是你自己刚生成的创作物时，首轮的广度还要花在方案上。** 单一方案打磨得越完整，评测越早被锁进它的局部修补——办成事的读者不会替你质疑结构，他们只报告受阻，而受阻天然是元素级的。首轮就拿两三个**结构前提不同**的候选（各自一句话写明前提）同批盲测对跑，让证据在方案之间选择和杂交；结构定了，后面的轮次才轮到打磨。姿势见 protocol.md §9。

**动笔写第一个 persona 之前，先完整读 [references/cast.md](references/cast.md)。** 仿真用户自己就是个 agent，它在陌生界面上凭「想起了什么」决定下一步——所以人设的重心是 `memory`（他具体经历过什么，带具名工具、年份、翻过的车），其次是 `skills`（他的操作流），`profile` 只是恒常驻的身份锚，短就对了。倒着写：先攒经历 → 再抽本事 → 最后蒸出身份锚。

只有身份标签、没有可召回经历的人设，会让几个 case 跑出同一份 trace——看着像多视角，其实是一个「积极的平均人」。定稿前跑一次 `python3 scripts/check-cast.py <persona.json> --scenario <scenario.json> --target "<被测物名>"`：它报密度缺口、**这个人在这个场景下哪几条经历会真的浮现**（引擎同一套打分），以及人和事里有没有漏进被测物的评价。

如果目标依赖大量项目细节，由主代理先理解这些细节，再把子代理完成任务真正需要的能力封装成 Local Use。Use 给它一个清楚的“能做什么”，隐藏无关装配；不要把整个仓库、内部实现、评价口径或预期问题塞给它。

被测目标在一个项目仓库里时，先按 [references/equip.md](references/equip.md) 盘点产品的操作面：源码只许主代理读来搞清产品怎么用，抽取的 use 一律是产品运行后经它自身入口可用的能力（产品 CLI、HTTP API、界面操作等），不是构建、脚本这类工程能力；模拟过程中子代理只接触构建并运行起来的产品产物，源码不进 case 可见范围。评测装置自身缺能力（录屏、批量造数、专项检查等）时，也按同页流程调研并引入现成的外部 skill，而不是立即降级或手搓。

## 引导模式(可选)

默认不启用:eval 仍自主、少打扰,信息足够就直接推进。仅当用户要求参与配置时进入(详细合同见 [references/guided.md](references/guided.md))。

- **何时进入**:用户说"引导我 / 一步步问我 / 带我配一下 / guided";或需求特别模糊且用户没说"自主 / 别问我"时,提议一次,拒绝即回默认。
- **进入后先告知一句**:本次模拟默认在你本地运行(你的机器出算力、浏览器/shell,子代理扮演各类用户),不提交服务端,结果默认只留在本地。
- **逐步小问**:在几个高杠杆决策点(验证问题&分析口径&深度 / 共享情境 / 人群 / 场景 / 规模&入口 / 要不要量化)停下征询,每点带推荐默认;整套运行配置始终暴露、可就地改。
- **情境 / persona / scenario 必看(引导核心)**:派发前把共享开场情境、每个虚拟用户是谁、要办什么事的人话摘要一次性亮给用户、请其提修改方向,即便走快速通道也先亮一眼——默认 eval 自造且用户看不到,这是引导最该让用户参与的部分。三者属轨迹层,只写客观事实、不注入评测口径。
- 服务端大规模真端仿真本期不支持:eval 只在本地跑;平台留档默认关闭,用户明确要才做。

## 运行

组装或执行任何 case 前，完整阅读 [references/protocol.md](references/protocol.md)。它定义 Methodology、Local Use、session、隔离、preflight、子代理指令、trace、evidence 与 bundle 的准确合同。同时阅读 [references/orchestration.md](references/orchestration.md)：它规定子代理推进 case 的两层循环——规划层（观察→思考→稀疏动作，done 须过终态闸）与执行层（观察→动作→验证效果，无进展熔断、预算收口）。

界面类 case 的真浏览器，**派发前必读** [references/browser.md](references/browser.md)：web（网页）case 走 agent-browser，隔离资源怎么造、子代理怎么驱动、截图怎么落进 evidence 都在那页。**app 端（Android / iOS / mac 应用）的驱动已退役**（simulator 的 MCP 注入随 #498 撤走，GUI 控制交给 pi-gui），**app 类 case 目前一律不派**，缘由与边界见 [references/app-cases.md](references/app-cases.md)。两页共守同一条红线：**绝不驱动用户自己的浏览器与应用**，它优先于任何工具便利。

每个 case 使用独立子代理或无历史的新进程。只给它自己的 persona、scenario、共享的客观情境、目标入口、必要的 use、可见范围和 trace 合同。不要给 analysis、measure、owner 的担忧、其他 case、历史 feedback 或修改意图。

让它通过真实入口办事：能打开就真打开，能运行就真运行，能观察就保存证据。工具或环境失败属于 execution error，不是用户放弃；无法获得真实体验时就说明限制，不用源码阅读或想象冒充成功。

子代理拥有某个工具，不代表 persona 突然具备使用它的知识。只能让工具执行这个人现实中会做的动作；只有 shell 时不能把命令执行写成“点击了界面”，也不能借 Local Use 绕过正在验证的入口。主代理必须把实际工具记录与 trace 对照，动作、观察或证据不一致的 case 作废并在干净环境重跑，不能进入反馈。

## 把反馈还给当前工作

主代理结合验证问题阅读所有 trace，依次分清：

- 直接观察到的行为与结果；
- 有证据支持的解释；
- 尚未验证的推断；
- 执行环境问题与目标本身的问题；
- 多个视角的共同模式、特定约束和真实分歧；
- **办成了事但办得费劲的地方**：首步的情绪、耗在无关区域的步数、说出口的抱怨，以及最值钱的——「要是我来做会长成什么样」式的话。succeeded 的 trace 里只有这一层藏着结构信号，第一遍按结果读完，必须再按摩擦读一遍。

按与用户目标的相关性、后果、证据强度和覆盖范围确定优先级，不按出现次数简单投票。默认给语义化反馈：这次回答了什么、发生了什么、它改变了哪些判断、下一步建议做什么、还剩哪些取舍。只有数字确实帮助当前决定时才量化。

**报告第一节固定是 TL;DR**，写在 `feedback.md` 最前面（标题就用 `## TL;DR`）：三到五条，每条一句话，先说结论再说依据出处；把最该被看见的判断、最疼的受阻点和最高优先级的需求放进去；不铺垫背景、不复述方法、不摆没有结论的数字。后面各节照旧展开，TL;DR 只是入口而非摘要式重写。查看服务的 run 列表用 `feedback.md` 第一行非标题文本当结论摘要，所以 TL;DR 的第一句同时是这条 run 在列表里的门面——把最重要的那句放第一条。

反馈里的改进建议写成**产品新需求**：每条说清哪类用户、在什么处境、需要得到什么结果，以及证据回指——这是产品层的诉求陈述，交给目标的 owner 决定怎么实现。需求条目的完整形态见 protocol.md §9。只有用户已明确授权本次直接修改目标（Loop）时，才在需求之外另列你打算怎么改。

## 需要 Loop 时

把反馈直接用于已获授权的当前工作。修改前保留被验证版本和指纹；修改后用干净上下文复验真正受影响的路径。无需机械重跑全部 cases，也无需跑满任何轮数。复验范围怎么选、何时算收敛，默认规则见 protocol.md §9。

**先判该补还是该另起。** 每轮显式判一次：不判就会一直在同一个地基上打补丁，补到最后谁也没问过这个地基对不对。

信号从证据里读，不凭手感：不同用户受阻的落点是同一个结构层级而非同一个元素；这轮要补的几件事在抢同一个稀缺位置（第一屏、开头几十秒、主操作位）；连着两轮某一维在涨、另一维钉住；改动清单几乎全是「再加一块」；有人每轮都自己动手返工同一处；现在的组织方式建立在一个用户并不关心的前提上。命中两条以上，至少产一个另起结构的候选。

**判补丁不是默认档，是需要交代的结论。** 把上面这几条信号逐条对一遍写进 feedback，说清每条为什么不成立。只写一句「受阻点是局部的」就算判过，那这句每轮都写得出来——于是每轮都在同一个地基上补，没有一轮真的问过这个地基。

**判之前先换手。** 目标是你做的，你给自己的地基判补丁天然可信度不足——沉没成本不是自律能中和的。轻则强制自问「假如这版不是我做的，只看 traces 和 feedback 我会怎么判」并把答案写进留档；拿不准就 spawn 一个只读证据、不看目标本身也不知道作者是谁的子代理出判定建议，要推翻它就把反驳一并落档。

反过来也要显式说：受阻点都落在具体元素上、上一轮已经把钉住那维推动了、或剩下的缺口是缺事实（要 owner 提供）而不是结构问题——地基还在做功，拆了是浪费。**说不出你要换掉的是哪条前提，就是在换皮，换皮不算另起。**

**另起版别自己动手——隔离生成。** 你脑子里装着现版本的每一块，亲手做的「另起」多半塌成减法换皮。把素材事实、需求清单和新前提交给一个**没见过任何现版本**的子代理从零出结构，你只做事实核对；它没见过原来的皮，换皮在机制上就不可能。

**用户给出的具体替代结构，有强制力。** 任何 case 里出现「应该长成什么样」的具体描述（分成几页、换成什么主轴、砍掉哪一层），下一轮必须把它实现成对跑候选之一，不许只归档进需求清单——那是整场评测里最贵的证据，晾一轮就浪费一轮。

另起必须赢：与现版本跑同一批 case、同一口径、各自全新上下文，且两版事实基础一致（可以把旧版只是声称的东西真的展示出来，不许引入旧版没有的新事实——否则赢的是新内容不是新结构）。赢才换；输了如实说「另起的更差，保留原版」并留档，不因为花了功夫就采用。平局也不算赢——真要换就把例外依据写进留档，让人能反驳。换皮或只改文案的轮次一样过这道闸，只是不领另起的名。留档格式见 [references/protocol.md](references/protocol.md) §9。

声称“这个问题已修复”，需要受影响用户的新行为证据；声称“整体更好”，需要可比较的前后版本与同口径 trace；声称“充分完成”，还要加入没看过修改过程的新视角。若 persona 或 scenario 已改变，明确这是覆盖范围变化，不能把不可比结果说成提升。

不要为了得到顺利 trace 制造假链接、假数据或假成功。真实能力尚不存在时，如实暴露限制，并把它作为反馈的一部分。

## 留痕

**本地 session 目录是第一留痕位置**，固定建在 `~/.mirasim/eval/sessions/<slug>/`（`MIRASIM_HOME` 设置时替换 `~/.mirasim`；slug 用 `<yyMMdd-HHmm>-<被测物短名>`，目录内文件合同见 protocol.md §1）。mirasim 自带的 eval 查看服务从这里读记录，列出全部 run、逐 case 展开轨迹与截图。不要把轨迹摘要当成留痕的替代。

**本轮是本地跑（未接平台）且跑在 mirasim 里时，跑完必须把这次 run 的查看链接交给用户**，别让他自己去找。这两个条件都由环境自己回答，不要问用户：

- 环境变量 `MIRASIM_EVAL_VIEWER` 存在 ⇒ 你正跑在 mirasim 里，查看服务已经在跑。直接给出这次 run 的深链 `<MIRASIM_EVAL_VIEWER>run/<slug>`（例：`http://127.0.0.1:4970/eval/run/260805-1832-mirasim-site`），一并说明它是本地记录、点开即看。不要另起 `mirasim eval`，不要让用户自己拼 URL。
- 该变量不存在 ⇒ 在裸 CLI 里跑。给出 session 目录绝对路径，并告诉用户 `mirasim eval` 可以起本地页面复核。
- 链接注定打不开时（例如 agent 跑在远端而用户的浏览器在本机）说明这一点并退回给路径，不要甩一个死链。
- 本轮接了平台（用户明确要求，见下）⇒ 这条不适用：留档与回执按 cli.md 的姿势走，不必额外推本地链接。

平台留档（**默认关闭**）：默认到此为止 —— 本地 session 就是完整留痕。不要探测 CLI、不要运行 `scripts/ensure-cli.sh`、不要提示用户去装或登录；session 状态记 `local_only`，**不标 `pending_upload`**（那是"要传但暂时传不了"，默认根本不打算传）。

用户明确要求接平台后才做这一段：先运行本技能目录的 `scripts/ensure-cli.sh`（用绝对路径执行——宿主的当前目录通常不在技能目录）：它按 `MIROFISH_BIN` → PATH 已装/开发版 → 固定地址安装的顺序确保 mirofish CLI 可用，只装缺失、绝不覆盖本地版本。装好后 `mirofish doctor --json` 确认登录态再继续；确实装不上或未登录时不阻塞本地仿真，如实告知并按 `pending_upload` 留痕。

要接平台时（检索资产、准备上送、恢复待补传 session），完整阅读 [references/cli.md](references/cli.md)；没接就整页不用读。

**接了平台就随做随写**：启用之后，回写不是收尾一次性动作，而是边做边写：

- **资产生成即回写**：新造的 persona / scenario 定稿即 `create` 落库拿远端 id，methodology 组装完成即 create——不要等仿真跑完才补录。复用的资产本就有 id。
- **run 跑完即回写**：每次执行的全部 case 到达终态后，立即把**完整轨迹** ingest 成一条 run——含执行证据：GUI(browser/mobile) case 每个 operate 的截图、CLI(shell) case 每步的命令与输出（trace 合同见 protocol.md，上送姿势见 cli.md 的 `--evidence`）。语义反馈写好后随 `--report` 一并回传或事后 `runs report` 补。多轮 loop 每轮各回写一条 run，用 evol 串成谱系（evol＝同一目标多轮验证的版本链，姿势见 cli.md §6）。

启用中途用户说不回写就即刻停手、全程只留在本地。脱敏红线照守：token、cookie、密码、API key、个人身份、本地绝对路径、Local Use binding、无关源码、费用与模型隐藏推理绝不上传；**截图也是证据**——上传前检查画面里没有凭据或个人信息，有就打码或不传（脱敏见 cli.md）。修正同一份记录的漏记或格式错误时更新原 run；重新执行、换模型、补跑用户或验证新版本时创建新 run，并按需串入同一 evol 谱系。

CLI 不可用不应阻塞本地工作。无论是否接平台，都生成可校验、可补传的完整 session，不要只留一段主代理总结。

## 不可妥协的证据边界

- 保存用户原始请求、目标版本与指纹、每个子代理实际收到的完整指令、原始 trace、外部证据、反馈、bundle、版本差异，以及接了平台时的上传回执。
- Trace 必须忠实描述实际工具、入口和结果；persona 的能力边界不能被执行代理自身的能力悄悄补齐。
- `thought` 只保存可公开的简短决策理由，不索取或留存隐藏思维链。
- 上传前清理凭据、cookie、个人数据、本地绑定和无关源码；脱敏秘密，不美化行为。
- 仿真用户的反应是视角，不是产品裁决。最终取舍仍属于用户和主代理。
