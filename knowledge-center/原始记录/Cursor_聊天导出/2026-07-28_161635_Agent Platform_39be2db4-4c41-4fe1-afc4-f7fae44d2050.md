## 结论：不要把整卡改成「审核中」

已上架智能体提交**新版本**或**权限变更**时，推荐采用 **「智能体状态」与「版本/变更审核状态」分离** 的模式（类似应用商店的 staged release / 蓝绿发布）：

| 维度 | 首次发布（未上架） | 已上架后再发版/改权限 |
|------|-------------------|----------------------|
| **智能体主状态** | 草稿 → 审核中 → 已上架 | **保持「已上架」不变** |
| **用户端可见性** | 审核中不可见 | **继续可见、继续可用** |
| **用户实际使用的版本** | — | **当前线上版本（live）** |
| **待审内容** | 整卡首次发布 | **候选版本 pending** 或 **权限变更单** |
| **审核通过后** | 首次上架 | **原子切换**到新版/新权限 |
| **审核驳回后** | 回到已驳回 | **线上版不变**，仅候选版驳回 |

详细设计里已有这条原则：

> **更新后**：智能体原版本保留不变；新版本需重新走审核；**旧版本在审核期间继续保持运行**  
> — `详细设计-02-智能体管理与工具开发.md` §4.2

## 推荐状态模型（运营端展示）

运营卡片/详情建议拆成两层信息，而不是单一「审核中」：

```
智能体状态：已上架
发布状态：v1.2 审核中（线上仍为 v1.1）
```

或更结构化：

| 字段 | 含义 |
|------|------|
| `status` | 草稿 / 已上架 / 已停用 / 已下架 / 已驳回（**仅首次从未上架时**才用审核中） |
| `liveVersion` | 用户正在用的版本 |
| `pendingRelease` | `{ version, note, submittedAt, auditStatus: 审核中\|已驳回 }` |

**用户端过滤规则**（与 PRD 一致）：

- 只看 `status === 已上架` + 权限匹配  
- **不看** `pendingRelease.auditStatus`  
- 运行时路由到 `liveVersion`，不是 pending

**运营端展示**：

- 卡片标签：`已上架` + 角标 `新版本审核中`  
- 详情横幅：`v1.2 发布审核进行中，用户仍可使用 v1.1`  
- 审核工作台：照常审 pending 版本，Diff 为「候选 vs 线上」

## 各场景怎么处理

### 1. 已上架 → 发新版本（最常见）

- 主状态：**已上架**  
- 用户：**继续用旧版**  
- 审核通过：切换 `liveVersion`，清掉 pending  
- 审核驳回：主状态仍已上架，pending 标为已驳回，创建者可改后重提

### 2. 已上架 → 改可见范围（组织/全公司）

- 主状态：**已上架**  
- 生效范围：**仍用旧范围**  
- 审核通过：切换为新范围  
- 避免「改范围审核中 → 全员看不见」

### 3. 已上架 → 停用 / 下架

- 这是**运营主动治理**，不是发版审核  
- 应直接走「已停用 / 已下架」，与用户端下线预期一致

### 4. 审核很久怎么办（体验兜底）

- **SLA 提醒**：审核工作台等待 >3 天标橙、>7 天标红（详细设计 §6.1 已有）  
- **撤回候选版**：创建者可撤回 pending，不影响线上  
- **紧急回滚**：审核通过后若有问题，运营可一键回滚到上一 live 版本（可选增强）

## 一、用大白话讲清楚「已上架再改版本」该怎么走

可以把它想成 **App Store 更新**，不是 **店铺关门装修**。

### 两种完全不同的场景

| 场景 | 打个比方 | 用户能不能用 |
|------|----------|--------------|
| **第一次发布**（从没上过架） | 新 App 提交审核 | 不能，审核通过才上架 |
| **已经上架，再发新版本** | 微信 8.0 还在用，8.1 在审 | **能**，继续用旧版，新版审完再换 |

### 核心原则（一句话）

> **「审核中」说的是「新版本在排队」，不是「整个智能体关门了」。**

所以应该有两层信息，不能混成一个状态：

```
智能体本身：已上架（门还开着）
新版本：    v1.2 审核中（后厨在做新菜）
用户实际吃到的：还是 v1.1（旧菜继续卖）
```

审过了 → 悄悄换成 v1.2；驳回了 → 用户照常用 v1.1，创建者改完再提。

### 和「停用 / 下架」的区别

| 操作 | 含义 | 用户端 |
|------|------|--------|
| **发新版本审核** | 正常营业，后台换菜单 | 继续用旧版 |
| **停用** | 临时打烊，配置还在 | 不能用 |
| **下架** | 从货架撤掉 | 不能用（广场/侧栏不出现） |

只有 **从没上过架** 的首次发布，或者运营 **主动停用/下架**，才应该让用户看不见、用不了。

### 改权限也一样

已上架智能体把「仅部门 A」改成「全公司」，审核期间：

- **旧范围继续生效**（A 部门还能用）
- 新范围 **审过才生效**
- 不能把整卡变成「审核中」导致全员突然用不了

### A-01 运营侧到底几个状态？

| 来源 | 说法 |
|------|------|
| `运营平台-智能体运营-v2.md` | **6 态**：草稿、审核中、已上架、已停用、已下架、已驳回 |
| TASK-049 / `01-运营全景` | **7 态**，含「待发布」 |
| `05-agent-detail.html` UI | 仍显示「开发中」「待发布」 |
| `project-memory.md`（旧） | `dev → published_pending_review → listed → offline/rejected` |

**影响：** 筛选器、KPI、测试断言、文案对不上。  
**建议定稿：** 运营 SSOT = **6 态**；「开发中」「待发布」仅作时间线事件名，**不作为独立运营状态**。

### A-02 中英文 / 代码枚举不一致

### A-03 用户端 PRD 状态枚举与运营不一致

| 来源 | 枚举 |

**建议定稿：** 用户端数据契约只引用运营 6 态 + 个人草稿（用户私有，非运营态）；统一用「已驳回」。

### A-04 早期综合设计文档的 9+ 态

## B. 发布 / 审核 / 上架流程

### B-01 审核通过后还要不要「待上架」？

| 来源 | 说法 |
|------|------|
| **ADR-011（Accepted）** | 审核通过 → **直接已上架** |
| `运营平台-智能体运营-v2.md` | ✅ 一致 |
| `docs/功能清单-智能体运营.md` §1.3、§1.5 | ❌ 「审核通过 → **待上架** → 上架用户可见」 |
| **ADR-009**（较早） | 发布与上架拆成两步 |

**影响：** 审核工作台通过后下一步动作、用户何时可见，定义冲突。  
**建议定稿：** **审核通过 = 直接已上架**（ADR-011）；删除「待上架」中间态。

---

### B-02 全公司发布要不要「上级审批」？

| 来源 | 说法 |
|------|------|
| **ADR-011（Accepted）** | ❌ **移除**上级审批，仅平台审核 |
| `运营平台-智能体运营-v2.md` §4.4、§5.5、§5.6 | ✅ 全公司 → **上级审批** → 平台审核 |
| `05-agent-detail.html` 审核横幅 | 含「平台审核」节点（未明确上级） |

**影响：** 审核 stepper 节点数、角色权限、等待时长统计全变。  
**建议定稿：** 二选一写死 — **方案 A**：仅平台审核（改 ops-v2）；**方案 B**：恢复上级审批（改 ADR-011）。

---

### B-03 「发布」和「上架」是不是两个动作？

| 来源 | 说法 |
|------|------|
| `docs/功能清单` §1.1 卡片菜单 | 含「发布、**上架**、下架…」两个词 |
| ADR-010 / ADR-011 | 合并为一条 **发布** 链路 |
| ops-v2 §5.5 | 弹窗按钮「确认发布 / 提交审核」，无单独「上架」 |

**建议定稿：** 对外只保留「**发布**」；个人范围 = 发布即上架；组织/全公司 = 发布即提审。

### B-04 个人范围是否免审？

| 来源 | 说法 |
|------|------|
| ops-v2 / lifecycle / ADR-011 | ✅ 个人 → **直接已上架** |
| `proto.js` `requiresPublishAudit` | `private` 免审；`org/specific/public` 须审 |
| ops-v2 权限筛选 | 写「个人 / 组织 / **公开**」 |
| proto 筛选 | `private / org / specific / public` |

**影响：** 「组织」与「部门共享(specific)」是否同一档；「公开/全公司/public」是否同一档。  
**建议定稿：** 访问范围三档 — **个人 / 组织 / 全公司**，并映射到 `shareMode` 枚举。

## C. 已上架后再变更（核心缺口）

### C-01 已上架发新版本 → 整卡变「审核中」？

| 来源 | 说法 |
|------|------|
| `详细设计-02` §4.2 | ✅ **旧版本审核期间继续运行** |
| `agent-lifecycle-states.md` | ❌ 未画「已上架后再发版」；`已上架 → 权限变更 → 审核中` |
| `proto.js` `runAgentPublish` | ❌ 任意提审 → `status: 'review'` |
| `ops-v11-app.js` `applyPublishWithScope` | ❌ 须审 → `status: 'reviewing'`（不区分首次/再发版） |
| ops-v2 状态图 | ⚠️ **未定义**已上架后再发版路径 |

**影响：** 审核久 → 用户端看不见、用不了（`UserAgentResolver` 只认已上架）。  
**建议定稿：** 引入**双轨模型**：
- `status`（门店开不开）：已上架保持不变
- `pendingRelease`（新菜单审没审完）：审核中 / 已驳回
- 用户始终用 `liveVersion`，审过再切换

---

### C-02 已上架改可见范围 / 权限 → 整卡变「审核中」？

| 来源 | 说法 |
|------|------|
| `agent-lifecycle-states.md` | `已上架 → 权限变更 → 审核中` |
| `ops-v11-app.js` `openPermissionModal` | 组织/公开变更 → **`status: 'reviewing'`** |
| `05-agent-detail.html` | 「修改可见范围」走同一套 `runAgentPublish` |

**影响：** 改范围审核期间，原范围用户也可能突然不可用。  
**建议定稿：** 与 C-01 相同 — `pendingScopeChange` 待审，**旧范围继续生效**。

---

### C-03 已上架智能体改配置（模型/知识库/Skills）要不要审？

| 来源 | 说法 |
|------|------|
| `详细设计-02` §4.3 | 提示「需提交**新版本**审核方可生效」 |
| ops-v2 / lifecycle | **未写**配置变更规则 |

**建议定稿：** 凡影响运行行为的变更，都走 **pendingRelease** 新版本审核；基本信息（名称/描述）可即时保存但不影响线上版本（详细设计 §4.1 已有）。

---

### C-04 已上架卡片能否「重新发布 / 发新版」？

| 来源 | 说法 |
|------|------|
| ops-v11 卡片菜单 | 已上架只有：停用、下架、权限 — **无「发新版」** |
| `05-agent-detail.html` | 已上架仍有右上角「**发布**」按钮 |
| ops-v2 §5.4 | 版本与发布 Tab 有发版信息 |

**影响：** 列表入口 vs 详情入口能力不一致。  
**建议定稿：** 发新版统一入口在**详情页「发布」**；列表卡片可选加角标「新版本审核中」。

## E. 用户端可见性与过滤

### E-01 用户端哪些状态可见？

| 来源 | 说法 |
|------|------|
| 用户端 PRD §4.2 / §5.3 | 仅**已上架** + 权限匹配 |
| 用户端 PRD | 过滤：审核中 / 已下架 / **待审核** |
| ADR-013 | 过滤：`reviewing/offline/pending` |
| `user-agent-resolver.js` | 只认 `listed/published` |

**缺口：** **已停用** 未写入用户端 PRD；resolver 也未显式过滤 `disabled`。  
**建议定稿：** 用户端不可见 = 非已上架（含：草稿、审核中、**已停用**、已下架、已驳回、首次发布审核中）；**已上架+pending 新版审核中仍可见**（用 liveVersion）。

### E-02 已上架再发版审核中，用户端要不要显示？

| 来源 | 说法 |
|------|------|

**建议定稿：** 见 C-01；用户端**不感知** pending，除非产品要做「更新中」提示（可选，非必须）。

### E-03 下架后进行中的对话怎么办？

| 来源 | 说法 |
|------|------|

**建议定稿：** 用户端行为相同（均不可见、不可新开）；运营侧保留两态（停用可快速恢复，下架须走发布流程）。

# 建议写入 PRD 的「定稿模板」（你拍板后填 `[待定]`）

```markdown
## 智能体状态（SSOT）

### 1. 运营主状态（6 态）
| 状态 | 含义 | 用户端可见 | 卡片操作 |
|------|------|-----------|---------|
| 草稿 | 未对外 | 否 | 删除 |
| 审核中 | 首次发布待审 | 否 | 撤回、删除 |
| 已上架 | 对外可用 | 是（用 liveVersion） | 停用、下架、权限 |
| 已停用 | 临时不可见 | 否 | 启用、下架、删除 |
| 已下架 | 从入口移除 | 否 | 重新发布、删除 |
| 已驳回 | 首次发布被驳回 | 否 | 重新发布、删除 |

存储枚举：[待定 dev/review/listed/disabled/offline/rejected]

### 2. 发布审核子状态（双轨，仅 status=已上架 时）
| 字段 | 含义 |
|------|------|
| liveVersion | 用户正在使用的版本 |
| pendingRelease | 候选版本（含 version、note、auditStatus=审核中/已驳回） |
| pendingScopeChange | 候选访问范围（可选，结构同上） |

规则：
- 已上架后再发版/改范围：主状态保持已上架；pending 审过才切换 live。
- 首次从未上架：主状态=审核中；无 liveVersion。

### 3. 审核链路
[待定：仅平台审核 / 含上级审批]
- 个人：免审直接已上架
- 组织/全公司：须审核；通过后直接已上架（无待上架）

### 4. 用户端过滤
可见条件：opsStatus=已上架 AND 权限命中 AND 非已停用。
不感知 pendingRelease（除非后续做「更新中」提示）。

### 5. 个人智能体（用户端私有）
draft / synced — 与运营 6 态分离；同步到运营=草稿，不在用户端「提交审核」。
```

## 智能体状态 — 产品定稿 Tips（给团队看）

### 先记住一句话

**「审核中」说的是「新版本或新权限在排队」，不是「整个智能体关门了」。**  
已经在上架、用户正在用的智能体，不能因为发新版或改权限，就让所有人突然用不了。

---

### 一、状态怎么分（两层，别混成一个）

**第一层：门店开不开（6 个主状态）**

| 状态 | 大白话 | 用户能不能用 |
|------|--------|--------------|
| 草稿 | 还没对外 | 不能 |
| 审核中 | 第一次发布，还在审 | 不能 |
| 已上架 | 正常营业 | **能** |
| 已停用 | 临时打烊，配置还在 | 不能 |
| 已下架 | 从货架撤了 | 不能 |
| 已驳回 | 第一次发布被否了 | 不能 |

**第二层：已上架之后，有没有「待审的变更」**

- **线上版本**：用户现在实际在用的版本  
- **待审变更**：新版本或新权限，审完才生效  

已上架 + 有待审变更时，对外仍显示「已上架」，用户继续用旧版；运营后台可加角标「有新版本审核中」。

---

### 二、几个容易搞混的场景，统一这样定

**1. 第一次发布（从没上过架）**  
提交 → 主状态变「审核中」→ 用户看不见 → 通过 → 「已上架」→ 用户可见。  
驳回 → 「已驳回」，改完可**同一个智能体**重新提交，**不用重新建一个**。

**2. 已经上架，再发新版本**  
主状态**保持「已上架」**；待审的是新版本。  
用户继续用旧版；审过再切新版；驳回则线上不变，创建者改完再提。

**3. 已经上架，改可见范围（比如从某部门扩到全公司）**  
主状态**保持「已上架」**；待审的是新范围。  
**旧范围继续生效**，审过再切新范围。不能把整卡变成「审核中」导致原用户也用不了。

**4. 停用 vs 下架**  
- **停用**：临时关一下，运营可一键恢复，不用重新走发布。  
- **下架**：从用户入口拿掉，要再上线得走「重新发布」。  
用户侧：两种都**看不见、不能新开对话**；区别在运营怎么恢复。

**5. 个人 / 组织 / 全公司，审不审？**  
- **仅个人**：发布即上架，免审。  
- **组织或全公司**：须审核；**通过后直接上架**，中间不要再加「待上架」一步。

**6. 要不要「上级审批」？**  
团队需二选一并写死：  
- **方案 A**：只有平台审核（链路短）；  
- **方案 B**：全公司发布先上级、再平台（多一环）。  
不要有的文档写要、有的写不要。

---

### 三、和用户端怎么对齐（别人只看这条就够）

用户端（对话、广场）只认：

> **运营状态 = 已上架 + 当前用户有权限**

以下都**不出现、不可用**：草稿、审核中（仅指首次）、已停用、已下架、已驳回。  

**特别说明：** 已上架但「新版本在审」时，用户**仍应可见、仍用旧版**；不要把这类情况当成「审核中」整卡下线。

个人空间里「从历史对话存的智能体」：  
用户端只是**草稿**；同步到运营后是**运营草稿**，文案用「同步到运营平台」，不要说「提交审核」——真正发布/提审在运营后台做。

---

### 四、历史上文档不一致的地方，定稿时按下面收口

| 容易冲突的说法 | 建议统一成 |
|----------------|------------|
| 7 个状态（含「待发布」「开发中」） | 对外只认 **6 个主状态**；「待发布」等只当时间线事件，不当独立状态 |
| 「已拒绝」/「已提交」 | 统一用 **已驳回**；用户端「已提交」改为 **已同步**（若指同步到运营） |
| 审核通过还要「待上架」 | **不要**；通过 = 直接已上架 |
| 「发布」和「上架」两个按钮 | 对外只保留 **发布**（个人=直接上架，组织/全公司=提审） |
| 已驳回 = 终态、要重新建 ID | **不要**；同一智能体改完可重提 |
| 已上架改版权限 → 整卡变审核中 | **不要**；用「待审变更」，主状态仍已上架 |
| 「可见范围」/「公开」/「全公司」混用 | 统一：**访问范围** = 个人 / 组织 / **全公司** |
| 下架后正在聊的对话 | 需补一条：默认**不许新开**；进行中的会话「聊完再断」或「立刻断」可配置 |
| 专家审核、停止维护、归档 | 若本期不做，PRD 里标「后续」；主流程只写 6 态 |

---

### 五、给写 PRD / 做原型的人一句检查清单

定稿前自问五句：

1. 这是**第一次发布**，还是**已上架后的变更**？后者不能把主状态改成审核中。  
2. 用户端过滤看的是**主状态**，不是「有没有待审新版本」。  
3. 审核通过后是否**直接上架**？中间有没有多余的「待上架」？  
4. 全公司发布要不要**上级审批**？全文是否一致？  
5. 驳回后能不能**同一个智能体重提**？用户端有没有写错成「重新注册」？
