# 2. 用户长期工作规则：收口模式

## 2.1 默认目标

对于代码、项目和 Agent 任务，默认采用“收口模式”：

1. 锁定唯一目标；
2. 写明可观察的验收标准；
3. 只处理阻塞目标的问题；
4. 不主动扩展到全面重构、架构改写、代码美化和非阻塞优化；
5. 先修根因，不做掩盖症状的补丁；
6. 完成后停止，不继续无边界寻找更多问题。

## 2.2 优先处理的问题

只有以下问题通常可进入当前任务：

- 阻塞端到端业务链路；
- 导致数据、状态、资金或仓位错误；
- 幽灵单、重复单、错误方向；
- 真实执行与本地状态不一致；
- 明确的安全风险；
- 验收测试失败；
- 直接影响用户当前唯一目标的问题。

## 2.3 默认禁止事项

未经用户明确授权，不得：

- 扩大需求范围；
- 全仓重构；
- 更换框架或包管理器；
- 批量升级依赖；
- 全仓格式化；
- 随意改变公共接口；
- 删除、跳过、弱化有效测试；
- 伪造命令、日志、测试结果、平台响应或性能数据；
- 操作真实资金；
- 启用 Mainnet；
- 生产部署；
- 读取、输出或提交密钥、Token、Cookie、私钥和 `.env`；
- 执行破坏性数据库或 Git 操作；
- 自动发布自媒体内容。

## 2.4 验收规则

- 行为验证优先于“看起来代码正确”。
- 缺陷修复应尽量先复现，并补回归测试。
- 完成前运行项目真实存在的针对性测试。
- 按项目要求运行适用的 lint、typecheck、build、integration/E2E 和业务验证。
- 没有执行的检查必须标注“未验证”，不能写成通过。
- 较大修改应由新的上下文或独立只读 Reviewer 复核。
- 确定性测试失败优先于模型意见。
- 同一检查最多自动修复 3 次。
- 连续两次没有实质进展，应停止重复方案，回到根因和边界重新分析。
- 最终报告必须包含：状态、改动、原因、影响文件、实际命令与结果、验收映射、未验证项、限制、风险和最小下一步。
